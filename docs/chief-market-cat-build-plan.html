Executive Summary

Where We Stand

Chief Market Cat (CMC) is a supervised global market intelligence and trading decision-support system. Its job is to monitor market, news, macro, portfolio, and broker-state signals, then convert them into structured watchlist items, trade decision memos, and human review queues. It is not an autonomous trading bot — and will not be until a strict set of safety gates are in place.

The scaffold is done. The plumbing is not. Every module exists, the schemas are clean, and the config architecture is well-designed — but the pipeline currently produces no output. Both fetcher functions return empty lists, the classifier returns a placeholder, alerts are not sent, and the journal is not persisted. The project is structurally sound but operationally inert.

The target pipeline is 13 stages long, running from a scheduler through fetch → normalize → deduplicate → evidence_state → classify → verify → risk_gate → score → summarize → alert → journal. Of these, 6 stages are genuinely functional (normalize, deduplicate, evidence_state, verify_signal, risk_gate, score_watchlist), 3 are working stubs (summarize_brief, jsonl_store, alert_human), and 4 are empty or hollow (fetch_market_data, fetch_news_macro, classify_signal, run.py itself).

The most important finding: run.py does not call any pipeline stages. It just returns scaffold_ready. Before anything else matters, the pipeline stages need to be wired together in the entrypoint.

Beyond the plumbing gaps, there are 9 strategic gaps that need decisions before the system becomes useful: from picking a watchlist of tickers to deciding how human override patterns get captured, to managing data staleness across a 24/7 global market universe.

Design Philosophy

Deterministic modules first. LLM judgment only where useful. Evidence state before classification. Verify gate before scoring. Risk gate before any trade candidate. Human review for weak-evidence or high-impact signals. No autonomous live execution.

9 Critical Gaps

Must Resolve Before MVP
1

Watchlist Is Undefined — Pick 15 Tickers First

Critical

The score_watchlist pipeline stage has a complete, functional 6-factor weighted scoring algorithm — but it has nothing to score. portfolio.yaml defines six watchlist categories (global_indices, equities, ETFs, FX, crypto, commodities) and all six are empty lists. Without tickers, every upstream fetcher call returns nothing, and the pipeline produces zero output even if everything else is wired correctly.

portfolio.yaml → watchlists: { global_indices: [], equities: [], etfs: [], fx: [], crypto: [], commodities: [] }
Fix: Pick 10–15 starting tickers before writing a single line of connector code. Suggested starting set: 3–4 global indices (SPY/SPX, ASX200, Nasdaq, Nikkei), 4–5 quality equities (mix of ASX and US), 2 FX pairs (AUD/USD, USD/JPY), 1–2 commodities (Gold, Oil), 1 crypto (BTC or ETH). Without this decision, nothing else in the pipeline is testable.
2

run.py Is Not Wired — Pipeline Stages Never Execute

Critical

The entrypoint run.py loads config and immediately returns {"status": "scaffold_ready"}. It calls none of the 13 pipeline stages. This means even if the fetchers were connected, normalize, deduplicate, evidence_state, classify, verify, risk_gate, score, summarize, alert, and journal would never be invoked. The pipeline is architecturally correct but structurally unexecuted.

run_pipeline() → loads config → returns {"status": "scaffold_ready"} # no stages called
Fix: Wire the manual-input MVP flow first: manual_items → normalize → evidence_state → verify_signal → brief. Accept a list of hand-crafted RawMarketItems, pass them through the functional stages, and generate a brief. This creates a fully testable end-to-end pipeline run without needing real data connectors.
3

No Live Data Connectors — All Fetchers Return Empty Lists

Critical

Both fetch_market_data.py and fetch_news_macro.py are one-liners that return []. sources.yaml has all sources set to connector: manual. The Connector protocol in base.py is defined but no real connector implements it. The market data, news, and macro calendar connectors are all stubs.

fetch_market_data.py: def fetch_market_data(_cfg) → return [] fetch_news_macro.py: def fetch_news_macro(_cfg) → return []
Fix: Install yfinance (free, no API key) for market data as the first connector. It supports prices, volume, and historical data for most global indices and equities. Wire it into fetch_market_data to pull closing prices for the watchlist tickers. This unlocks normalize → deduplicate → evidence_state without needing any API key or paid subscription.
4

No LLM Provider Wired — Classify and Brief Are Both Placeholders

Critical

pipeline.yaml has classification.model: placeholder. The classify_signal.py function ignores its prompt file and returns a "Phase 0 placeholder classification" for every item. summarize_brief.py generates a markdown template with no intelligence. The prompt files signal_classifier_prompt.txt and market_brief_prompt.txt exist but are never called. The LLM is the intelligence layer — without it, CMC has no classification capability.

pipeline.yaml → classification.model: placeholder classify_signal.py → returns SignalItem(signal_type="no_trade_unclear", rationale="Phase 0 placeholder")
Fix: Choose an LLM provider (Claude Haiku or GPT-4o-mini are cheapest at scale), install the SDK, and wire classify_signal.py to call the API with signal_classifier_prompt.txt. Validate the JSON schema output with pydantic or dataclass parsing. Replace model: placeholder in pipeline.yaml with the actual model string.
5

No Backtesting Plan Before Paper Trading

High

The roadmap jumps from MVP 1 (intelligence brief) directly to Phase 3 (paper trading) without a validation step. Paper trading on unvalidated signal logic means learning nothing — you don't know if results are due to the signals, the timing, random noise, or a bug in the pipeline. You need a backtest layer to validate that the scoring weights and classification logic produce useful signals on historical data before committing real time to paper trades.

Roadmap: MVP1 (brief) → Day 2 (risk gates) → Phase 3 (paper trading) ← missing: backtest validation
Fix: Between Day 2 and Phase 3, add a historical backtest step using yfinance's historical data. Load 90 days of daily closes, run the pipeline against that data, check what signals the classify stage generates, and manually review whether the held/passed/blocked routing makes sense. This does not require a full backtesting framework — just running the pipeline on past data and reading the output.
6

Global Markets = 24/7 Signals with No Staleness Management

High

CMC targets global markets across multiple time zones. Forex and crypto run 24/7. Asian equities open at 10am Tokyo time. The ASX opens at 10am AEST. US markets open at 9:30am ET. pipeline.yaml defines stale_data_minutes (intraday: 15, daily: 1440) but nothing enforces it. The verify_signal.py code doesn't check timestamps for freshness. This means a news item from 14 hours ago could surface as an active signal when the next market opens.

pipeline.yaml → verify.stale_data_minutes: {intraday: 15, daily: 1440} ← not implemented in verify_signal.py pipeline.yaml → run.timezone: Australia/Sydney ← but no timezone-aware market calendar
Fix: Add a staleness check to verify_signal.py that compares fetched_at against stale_data_minutes thresholds. Add a market calendar lookup (using exchange_calendars or a simple dict) to skip signals outside trading hours for relevant markets. Tag signals with their market timezone at normalize stage.
7

Learning Loop Has No Feedback Mechanism

High

The journal_store stage is designed to log every signal and decision. But nothing in the pipeline reads back from the journal to improve future scoring. The 6-factor weights in pipeline.yaml (relevance: 0.25, evidence: 0.25, etc.) are static defaults and will never update unless someone manually edits the YAML. The Execution + Journal Agent in the blue-sky architecture is meant to "evaluate outcomes" — but there's no connection between journal records and any weight-updating or signal recalibration step.

pipeline.yaml → scoring.weights: {relevance: 0.25, evidence: 0.25, ...} ← static, never updated from outcomes journal_store.py → def journal_event(event) → {"status": "not_persisted"} ← doesn't even write yet
Fix: Before building a full feedback loop, first fix journal persistence. Once trades and outcomes are being logged to JSONL files, add a weekly manual review step: compare signals that were classified as strong against their actual outcomes. Build a simple review script that reads the JSONL journal and shows which signal types had the best predictive value. Dynamic weight tuning comes later — manual review is Phase 3.
8

Human Override Patterns Aren't Tracked

Medium

CMC's design is explicitly supervised — the human reviews signals, decisions, and the review queue before any trade action occurs. But the current schema has no field for capturing what the human actually decided when shown a signal. When a signal is routed to the human review queue, there's no record of whether the human overrode, confirmed, dismissed, or escalated it. This makes it impossible to learn from human judgment patterns over time.

schemas/trades.py → decision enum: ["monitor", "research_deeper", "paper_trade_candidate", "reject", ...] ← but no human_override field, no override_reason, no outcome_actual
Fix: Add a human_review_outcome field to SignalItem or TradeMemo: one of confirmed / dismissed / escalated / overridden. Add an override_reason text field. This doesn't need UI — it can be filled manually via a review script or YAML edit for now. The data will be invaluable later when building the feedback loop or agent memory.
9

No Alert Delivery Channel — Briefs Die on Disk

Medium

alert_human.py returns {"status": "not_sent", "brief_chars": len(brief)}. The market brief is generated (via the template in summarize_brief.py) but goes nowhere. For CMC to be useful as a daily intelligence tool, the human needs to receive the brief somewhere — whether via Telegram message, email, or even a plain file saved to disk with a notification. Without delivery, the pipeline is a tree falling in a forest.

alert_human.py: def alert_human(brief, _cfg) → {"status": "not_sent", "brief_chars": len(brief)}
Fix: The easiest first delivery channel is a Telegram Bot (free, no server needed, works on mobile). Create a bot via @BotFather, store the token in .env, and send the brief text as a message. Alternatively, write the brief to data/briefs/YYYY-MM-DD.md as a minimum. Either way, the human needs to see output for CMC to be useful in its most basic form.

Safety Boundary — Non-Negotiable

⚠️ No Live Trading Until ALL Six Gates Are In Place

  • Written risk framework — documented and signed off
  • Broker execution review — order type, spread, slippage checked
  • Max-loss cap — configured, tested, enforced in code
  • Kill switch — tested in paper mode, disables trading on drawdown or error
  • Full audit log — every signal, decision, and outcome recorded

Design Motto

"CSC finds external strategic signals.
CDC finds internal customer signals.
CMC finds market signals, but Risk Guardian decides whether they are tradable."

CMC's job is to surface information and structure decisions — not to execute them. The human is always the final gate. Every strong opinion from CMC is a recommendation for review, not an instruction to act.
